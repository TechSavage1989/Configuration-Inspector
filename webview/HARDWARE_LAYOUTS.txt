Config Inspector 5.13.0 - hardware layouts and device-owned addressing

The app includes 91 hardware profiles covering 195 exact model/module identifiers, including 81 verified physical layouts and ten qualified model port-group profiles. The registry is in hardware.js. It complements explicit configuration fields and automatic exact-model community catalog downloads. Manufacturer sources are documented here and in the source registry. Hardware cards, interface details and the hardware report appendix omit manufacturer links.

Port types and rated capacity are separate from configured speed, interface use and fitted transceivers. The app never assumes that speed alone establishes RJ45 versus an optical cage. SFP/SFP+/SFP28 identify cage types; a fitted copper transceiver or DAC is not inferred from the cage. Shared RJ45/SFP interfaces use a combined symbol. Unknown hardware retains a neutral physical-port symbol and a layout-availability note.

Hardware identification
The Model / Identify model action accepts an exact model or SKU for a device, member or module. It is an explicit user annotation, separate from source configuration. Matching profiles activate connector and geometry mappings; exact-model catalog lookups use annotated device/member identities. JSON snapshots preserve annotations, including SonicWall snapshots. Reset restores the configuration identity. An unknown model retains a clearly qualified two-row port inventory and neutral connector symbols where there is no explicit or catalog media evidence. Model selection does not manufacture an installed module, fitted transceiver or network assignment.

Automatic future-device coverage
The existing NetBox Community exact-model catalog can supply connector type, capacity and public device specifications for models without an embedded layout. It does not define port coordinates and cannot prove physical geometry. No complete config-format-independent database establishes every manufacturer's chassis layout. Exact geometry remains bounded to verified models; omitted model/module identity or an unsupported hardware revision is reported, rather than guessed. Adding a new profile requires checking its manufacturer diagram and port numbering.

Rendering and limits
- Boards fit their container by default. CSS grid and proportional tracks retain bank alignment and port order; compact labels avoid repeating chassis/member/slot prefixes. Enlarge opts into a larger scrollable view, and Fit width restores containment. Full names, port capacity and connector information remain accessible. Small appliances stop expanding at their natural tile size. One-row banks can retain upper/lower row alignment beside two-row banks.
- Physical views are schematic port layouts rather than dimensioned chassis replicas. Bank order and physical port positions are retained in the complete view. Logical interfaces remain in separate functional groups.
- Hiding unused ports compacts visible port positions and removes connector banks with no visible ports. Connector groups retain their order and port labels. This filtered view closes gaps. Showing unused ports restores the complete physical arrangement, including row alignment and known positions.
- Chassis modules have distinct slot cards. Stack members have distinct device cards, their own models and member IDs. A management interface is outside the module-slot grid.
- Stacking sections expose individual members, their model, source fields and linked stacking ports.
- Configured VSF ports are assigned for stacking even without an IP address or VLAN. Their local member/link assignment is shown in the tile and primary details. Unknown remote peer wiring is not invented.
- For complete exports, an explicitly installed supported module or supported stack-member model can establish omitted ports. Such ports have no assumed administrative or VLAN defaults and are hidden as unconfigured unless the user chooses Show unused. Partial command files do not create omitted hardware ports.
- Exact model recognition is intentionally bounded. New models can be added to the source registry; explicit media and the existing catalog path continue to cover models without a verified geometric layout. Installed optics, chassis dimensions and empty/unreported modules are not invented.

Device IP addresses
Only addresses assigned to interface, VLAN interface or management records are listed. Primary, secondary and IPv6 addresses retain their owner and mask/prefix. Duplicate VLAN/SVI projections are consolidated. ACL matches, address objects, DNS servers, routes and remote networks are excluded. A file with no device-owned addresses stays empty. No fallback to the general IP inventory occurs.

Switch ACLs
ACL definitions have their own root and maintain ordered entries, direction and interface/VLAN links. Quoted names and VLAN attachments are interpreted. The original match expressions remain available. A definition does not establish that an ACL is attached.

Importer recovery
Unmatched quotes in unrecognized fragments can occur in sanitized files. The switch importer preserves their original fields and resumes at a recognized root section. Legitimate quoted banner/location/description fields retain multiline behavior. A wrapped port list with a leading-comma continuation remains in its original VLAN context. A slash continuation joins the original member/port expression without creating a false port. Repeated terminal captures are bounded to one hardware inventory, with duplicate VSF links removed. A single fixed member with bare port numbers never generates an additional prefixed copy of those ports. Recovery is recorded in the import notes.

Validation
Synthetic fixtures cover FortiOS model aliases, connector/capacity mappings, mixed stacks, module inventories, VSF roles, model-based omitted ports, source/snapshot retention, ACL links and device-only addresses. Browser checks verify physical positions, unused-port toggles, drawer links, reports, mobile containment and both themes. Ten supplied files were audited separately; private configuration contents and screenshots are not included in this source package. Native Windows startup and WebView2 runtime behavior remain untested in the Linux build environment.
